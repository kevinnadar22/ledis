# TCP and Ledis

TCP gives Ledis a **byte stream**, not a sequence of messages. The kernel and the network may split or merge data however they like: one `write` from the client might arrive in a single `Read`, across several reads, or bundled with bytes from the next command. The client is free to send a full RESP command in one shot or drip it out in halves (or smaller chunks); either way the server only sees the next slice of bytes when it calls `conn.Read`.

A command is **confirmed complete** only after the wire format says so, not when a read returns. Ledis uses [RESP](https://redis.io/docs/reference/protocol-spec/): client commands are arrays starting with `*` (for example `*2\r\n$4\r\nPING\r\n`). The parser reads that type byte, then the array length line (`\r\n`-terminated), then each argument—usually a bulk string `$<n>\r\n` followed by exactly `n` bytes and `\r\n`. Nested lengths in the header and in each `$` line tell you how many bytes still belong to this command; until every declared field and payload is present, the frame is incomplete. In `handleConnection`, a `bufio.Reader` wraps the connection and `resp.DecodeBulkStringsArrayFromReader` reads until one full array is on the wire (blocking for more TCP data mid-command), then `resp.Decode` turns that into a command. Leftover bytes stay in the buffer for the next command, including pipelined commands in one segment.
