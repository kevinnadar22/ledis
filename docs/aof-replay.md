# AOF replay

**Append-only file (`appendonly.aof`)** — When `-appendonly=true` (default), every mutating command is logged as a RESP array line to `./appendonly.aof` in the server’s working directory. After a restart, that log is replayed to rebuild memory before accepting clients. On startup, **`AOF.Replay`** (in `internal/persistence/aof.go`) reads the file from offset 0 and calls your callback once per logical command. **`Server.ReplayHandler()`** returns that callback: it runs each command on **one shared session** (same connection-less session for the whole file) so behavior stays consistent with a single client. Each log line is read with **`DecodeBulkStringsArrayFromReader`** (blocks until one full `*…` array is on the wire—the same framing as TCP) and turned into a **`datatypes.Command`** with **`resp.Decode`**. Normal entries go straight to the handler. **`MULTI`** starts buffering; queued lines are **not** applied until **`EXEC`**, when only the buffered commands run (the logged `MULTI` / `EXEC` arrays are markers, not extra DB ops by themselves).

If the file ends **mid-array** (power loss mid-write), the reader returns an error: Ledis **`truncate`s** the file to the last safe byte offset—**`ok`** (end of the last fully replayed command), or **`multiStart`** (start of an unfinished `MULTI` block) if a transaction never reached **`EXEC`**. That drops the broken tail on disk and skips applying it. If the array was read completely but **`resp.Decode`** fails, the bytes are treated as intact but unusable data: replay **returns an error** and does not truncate. Tests: **`cmd/test/aof_replay_test.go`**.
